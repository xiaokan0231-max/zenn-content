実際の Flink プロジェクトで、性能をどう観測するか、稼働状態をどう監視するか、
アラートの方針をどう決めるか。ここでは自分の経験を整理しておきます。

## 一、Flink WebUI

まず Flink WebUI について。

![Flink WebUI のジョブ一覧画面](/images/d88d5526ddc3defc186150d6ba2fb971.png)

ローカルのデバッグモードでは、WebUI はデフォルトでは有効になりません。

```java
StreamExecutionEnvironment.getExecutionEnvironment();
```

この初期化方法だと、ローカルデバッグでは WebUI が開きません。

```java
StreamExecutionEnvironment.createLocalEnvironmentWithWebUI(conf);
```

ローカルデバッグ時に WebUI を開くには、こちらの方法を使う必要があります。
あわせて pom ファイルに依存を追加します。

```xml
<dependency>
    <groupId>org.apache.flink</groupId>
    <artifactId>flink-runtime-web_2.11</artifactId>
    <version>${flink.version}</version>
</dependency>
```

on YARN モードの場合は前者の初期化方法を使う必要があり、
on YARN ではデフォルトで WebUI を参照できます。

### スループットを読む

以下は Kafka のデータを読み、Flink で処理して、別の Kafka に書き込むジョブです。

![Flink WebUI のジョブグラフ](/images/65bec350d2495e5db8bab60b4c25fe5d.png)

sink をクリックし、metrics から `Sink__sink.numRecordsInPerSecond` を選びます。
**並列度の数だけ選ぶ必要があります。** 並列度を50に設定していれば50回選ぶことになります。

![metrics で各並列度の numRecordsInPerSecond を表示した画面](/images/623d075d14649a1d8a9a17b4c60040cb.png)

source についても同じ操作をします。

上の画面から、このジョブの sink の合計速度は 560 × 3 = 1,680 件/s、
source の合計速度は 1,737 件/s と読めます。ほぼ一致しています。

### その速度が正常かどうかをどう判定するか

**1. kafka-eagle で Kafka トピックの書き込み速度を確認する**

![kafka-eagle でトピックの書き込み速度を確認している画面](/images/8e551af51fe02e067bb25b9cb3f20536.png)

Kafka の書き込み速度は 1.66k/s です。
今回の業務ロジックは入力と出力が 1:1 なので、
Flink の書き込み速度と Kafka の生産速度は一致していることになります。

ここで **Kafka の生産速度が Flink の source / sink 速度より明らかに高い**場合は、
Flink がバックプレッシャーを起こしており、性能が本番要件を満たしていないとほぼ断定できます。

**2. バックプレッシャーを直接見る**

では Kafka の書き込み速度と Flink の消費速度が一致していれば安心かというと、
そうとも限りません。Flink WebUI でバックプレッシャーの状況を直接確認する必要があります。

![BackPressure タブで Ratio が 0、status が OK になっている画面](/images/d44762458c623f0f0adae0ea865998a4.png)

この画面のように Ratio が 0 で status が OK であれば、正常です。

ここでバックプレッシャーが出ている場合、Flink の消費速度が
日常の生産速度にかろうじて等しいだけで、しかも滞留データがあるということです。
この状況はデータの補填（バックフィル）時に顕著に現れます。
ジョブの限界性能が日常の生産性能と同じか、わずかに上回る程度しかないと、
この状態に陥る確率がかなり高くなります。

そのため一般的に、**Flink ジョブを本番投入する前に限界性能をテストし、
最低でも日常速度の3倍、できれば10倍以上を確保する**ことを求めています。

### ボトルネックがどの段にあるかを特定する

以下は Kafka のデータを読み、処理して MySQL に書き込むジョブです。

![下流でバックプレッシャーが発生している Flink WebUI の画面](/images/0ebe894f2e474479e79e031a770f3077.png)

下流でバックプレッシャーが発生していますが、下流には `group by` などの一連の処理があるため、
このままではボトルネックがどこにあるか特定できません。
どの段でバックプレッシャーが起きているかを見るには、オペレータの結合を禁止します。

```java
env.disableOperatorChaining();
```

![全サブタスクのバックプレッシャー情報を採取した画面](/images/eaf5934393dd2cc48af8a95974331879.png)

こうすると全サブタスクのバックプレッシャー情報を採取できます。
**一番上のサブタスクから下に数えていって、最初に緑色（正常）になったところが原因です。**
上の画面では FlatMap が赤、sink が緑なので、バックプレッシャーは sink で起きている、
つまり MySQL の書き込み速度が要求を満たせず、上流の Flink 処理全体が律速されていると分かります。

もちろん原因が1つとは限りません。MySQL の書き込み性能を解決した後、
別の段でバックプレッシャーが出る可能性もあります。
ただこの方法なら一歩ずつ問題を特定し、狙いを定めて最適化していけます。

ここで避けたいのは、**ボトルネックを特定せずにとりあえず並列度を上げる**という対処です。
一時的に症状が消えることはありますが、クラスタ全体への負荷は大きく増えます。
1つのジョブが数百 GB を占めるようになると、それ自体がクラスタ不安定の要因になります。
どの段が詰まっているのかを先に確定させたほうが、結果的に近道になります。

## 二、Kafka 消費の監視

Flink は checkpoint のタイミングで Kafka クラスタにオフセットの消費情報を提出します。
そのため Kafka lag の角度だけで見ると、消費遅延は**鋸歯状のグラフ**になります。

これは checkpoint が3分、かつ Flink にバックプレッシャーが無い状態の Kafka lag 監視グラフです。

スクリプトでは以下のコマンドで Kafka の総 lag を取得できます。

```bash
kafka-consumer-groups.sh --bootstrap-server <BROKER> \
  --describe --group <GROUP> | awk '{sum += $5} END {print sum}'
```

ここで **Flink 消費仮想速度 F0** という概念を導入します。
Flink の checkpoint 間隔を t とすると、

```
F0 = lag / t
```

さらにアラート用の消費速度を F2 とし、日常速度に対する倍率を m として、

```
F2 = F1 × m
```

たとえば Flink ジョブの日常の消費速度が 167/s、ピークが 250/s のとき、
アラート倍率を2に設定します。**F0 > F2 となったときにアラートを発火**させます。

| 番号 | Kafka生産速度 | Flinkの状態 | アラート | アラート時刻 | 誤報か |
|---|---|---|---|---|---|
| 1 | 167 | 停止 | あり | 最遅で m×t | いいえ |
| 2 | 668 | 正常 | あり | F0 > F2 のとき | **はい** |
| 3 | 300 | 正常 | なし | — | いいえ |

Kafka lag だけで Flink ジョブの状態を監視すると、
ピーク時に**誤報が発生しうる**ことが分かります。
かといってアラート倍率を高くしすぎると、今度は検知の即時性が落ちます。

実際には業務状況に応じて適切な m と t を設定し、
ごくわずかな誤報を許容したうえで、リアルタイムジョブの障害をユーザーに意識させない、
というバランスを取ることになります。

## 三、YARN の監視

per job モードで運用しているので、YARN 上ではジョブが一意の名前を持ちます。
スクリプトでは以下の方法で件数を取得できます。

```bash
yarn application -list | grep <JOB_NAME> | wc -l
```

この件数が1未満なら Flink ジョブが落ちている、という単純明快な判定です。

ただし、**YARN クラスタ自体が落ちている**というケースもあります。
この場合、監視スクリプト側では両者を区別できません。

そこで Kafka lag の監視と組み合わせて判断します。
**Kafka lag が正常なのに YARN でジョブ情報が取得できない**なら、
YARN 側が落ちていて Flink ジョブ自体は正常に動いている可能性が高い、と読めます。

## まとめ

1. YARN・Kafka・Flink WebUI の3つを総合して Flink ジョブの健全性を判断する
2. 適切な m と t を設定し、誤報率を最小に、SLA を最高にする
3. **Flink プログラムの品質が第一。** 限界性能はピーク性能の2倍以上を確保する。
   監視はあくまで補助であり、Flink の最適化が不十分なら、
   どれだけ監視を積んでも高い SLA は保証できない
