## 前提

データ量はおよそ10億件超。ここに対してアドホッククエリを提供する必要がありました。
ユーザーが時間などの検索条件を能動的に入力でき、一定の前処理時間は許容できる、
そして毎日新しいデータが加わる、という条件です。

10億件超のデータは通常の RDBMS にはやや荷が重く、しかも日々増え続けます。
そこで Spark で計算を高速化する方針を取りました。

対象のクエリはこういう形です。

```sql
select count(*) a, b from table_a where ... group by a, b order by a
```

## Spark の実測

まず spark-local モードで、データ量を倍々に増やしながら測定しました。

| データ量 | table_a の倍数 | spark-local<br>i3 / DDR3 8G | spark-local<br>i7 / DDR4 32G | spark-yarn<br>5G・3core・3instance |
|---|---|---|---|---|
| 800万 | 1 | 0.512s | 0.4s | 0.771s |
| 1,600万 | 2 | 0.512s | 0.5s | 0.552s |
| 3,200万 | 4 | 0.794s | 0.68s | 0.579s |
| 6,400万 | 8 | 1.126s | 0.945s | 0.652s |
| 1億2,800万 | 16 | 1.968s | 1.4s | 0.922s |
| 2億5,600万 | 32 | 3.579s | 2.574s | 1.475s |
| 5億1,200万 | 64 | 6.928s | 5.001s | 3.384s |
| **10億2,400万** | 128 | **13.395s** | **9.528s** | **5.372s** |

ここから分かるのは、**単一 CPU コアの性能も Spark の性能に効く**ということです。
Spark クラスタの計算性能を見積もるとき、core の数や instance の数だけでなく、
1コアあたりの計算能力も見る必要があります。しかも**データ量が大きいほど差が開きます**。

もう一つ、spark-sql には特徴があります。
**同じ文であれば2回目、3回目の計算が初回より速くなります。**
同じ文を繰り返し実行すると時間は下降傾向を示し、一定値に落ち着きます。
おおむね2〜3回で最小値に達します。

10億件のレベルでも、YARN モードで3回ほど実行すれば**3秒前後**まで到達しました。
テスト用の小さなクラスタとしては十分満足できる結果で、
正規の Spark クラスタであればさらに良くなるはずです。アドホッククエリの用途には十分でしょう。

個人的な理解では、Spark には一定のキャッシュ機構があるものの、
そこまで多くをキャッシュするわけではありません。この点は後述の Kylin とは異なります。
Kylin は同じ文であれば2回目は間違いなく即座に返ります。

## Apache Kylin の実測

次に Kylin を試したところ、結果はかなり衝撃的でした。

Apache Kylin は Hadoop 上に SQL クエリインターフェースと多次元分析（OLAP）機能を提供する、
オープンソースの分散分析エンジンです。もともと eBay が開発してコミュニティへ寄贈したもので、
**巨大な Hive テーブルに対してサブ秒で応答できる**点が特徴です。

Kylin は Hive テーブルを前提とするので、まずデータを Hive に取り込みます。
インストールは公式の手順どおりで、サービスを起動して 7070 番ポートを開けば済みます。

Kylin で計算するには、まず Model を作ります。1つの Model が1つの Hive テーブルに対応し、
その Model の上に Cube を作ります。ここではデフォルトの Cube を作成しました。
Model 画面では作成した Cube のサイズ・レコード数・前回のビルド時刻などが確認できます。

Cube のビルドが成功すると状態が READY になり、クエリを投げられるようになります。
クエリ画面では、その文がどの project・どの cube を通ったか、所要時間などが確認できます。

先ほどと同じ3ノードのクラスタで測定した結果です。

| データ量 | Cube構築時間（全量） | SQL実行時間 |
|---|---|---|
| 800万 | 6.5min | 0.15s |
| 1億2,800万 | 48min | 0.15s |
| 2億5,600万 | 90.17min | 0.15s |
| 5億1,200万 | 142.40min | **実行エラー** |

5億件になると Cube の構築自体は成功するものの、SQL 実行でエラーになりました。
これは設定を詰めきれていなかったためだと考えています。

## 比較して分かったこと

Kylin のクエリ性能はかなり優秀で、**しかもクエリ時のリソース消費が非常に少ない**という特徴があります。
ここが Spark とは異なる点です。この性質により、同じ性能のクラスタであれば
**Kylin のほうがはるかに高い並行度を捌け、はるかに高いクエリ性能を提供できます**。

一方で Kylin の代償は、**長い Cube 構築時間とより多くのディスク消費**です。
また経験上、**Kylin の SQL サポートは spark-sql ほど手厚くありません**。
既存の RDBMS のクエリをビッグデータクラスタへ移行したいのであれば、
spark-sql のほうが適応性が高いでしょう。

Kylin も増分ビルドをサポートしてはいますが、Spark も増分更新に対応しているため、
データ準備にかかる時間は Spark と比べるとかなり長くなります。

### どちらを選ぶか

- **データの前処理時間を許容できる場合**（たとえば Cube 構築を深夜0時以降に回せる場合）
  → **Kylin** のほうが適しているかもしれません
- **データがリアルタイムに変化し、次元が多く、SQL が完全に不確定な場合**
  → **spark-sql** のほうが適しているでしょう

具体的にどちらを選ぶかは、やはりアプリケーションのシナリオ次第です。
