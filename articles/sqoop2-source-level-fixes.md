## はじめに

RDBMS から HDFS へのデータ取り込みに Sqoop2 1.99.6 を使っていた時期に、
ドキュメントや設定では解決できず、**最終的にソースコードを読んで原因を特定した不具合が5件**ありました。
当時の調査記録をまとめておきます。

対象は `connector-generic-jdbc` モジュールです。

```
sqoop-1.99.6-bin-hadoop200/connector/connector-generic-jdbc/src/main/java/
  org/apache/sqoop/connector/jdbc/
    GenericJdbcPartitioner.java
    GenericJdbcExtractor.java
```

## 1. パーティション列のカーディナリティが 1 のときにエラーになる

分割キー（PartitionColumn）に指定した列の**異なる値が1種類しかない**場合、
ジョブがエラーで落ちます。

原因は `GenericJdbcPartitioner.java` の分割数計算にありました。
カーディナリティが 1 のとき、分割幅の計算が想定外の値になり、そのまま例外に至ります。

境界値として「分割できない場合」を正しく扱うようソースを修正して回避しました。

## 2. `Null value allowed for the partition column = false` でも null が取り込まれる

ジョブのパラメータで
`Null value allowed for the partition column` を `false` にしているにもかかわらず、
パーティション列に null があってもエラーにならず、null のレコードが HDFS に取り込まれてしまう、
という現象がありました。

**結論としては、これは不具合ではありませんでした。**

このパラメータが `false` のときは、そもそも
「pid が null のレコードを取り込む map」が起動しません。
`true` のときにだけ起動します。したがって**エラーにならないのが正しい挙動**です。

調べてみて「仕様どおりだった」と分かった項目も、記録として残しておきます。
同じ挙動に戸惑う人が同じ調査を繰り返さずに済むためです。

## 3. 日付・時刻の扱いの問題

`GenericJdbcExtractor.java` 側で、日付・時刻型のデータを取り出す際の変換に問題がありました。
該当箇所を修正して対応しています。

## 4. Oracle で時刻型をパーティション列にするとエラーになる

Oracle を接続元にして、**時刻型の列をパーティション列（pid）に指定するとエラー**になります。

原因は、生成される WHERE 条件の日付リテラルが Oracle の書式解釈に合わないことでした。
そこで **Oracle のときだけ `to_timestamp()` を使う分岐**を入れています。

```java
if (JDBC_DRIVER_ORACLE.equals(jdbcDriver)) {
    // Oracle の場合は特別扱いする
    conditions.append("to_timestamp('")
              .append(sdf.format((java.util.Date) lowerBound))
              .append("','yyyy-mm-dd hh24:mi:ss')");
} else {
    // 従来どおり
}
```

JDBC ドライバごとに日付リテラルの解釈が違うため、
**共通コードのままでは特定の DB でだけ落ちる**という典型的なパターンでした。

## 5. 西暦1000年より前の日付でエラーになる

時刻をパーティション列に使ったとき、
**データに西暦1000年より前の日付が含まれるとエラー**になります。

原因は日付文字列のフォーマット処理で、**年の桁を4桁にゼロ埋めしていなかった**ことです。
年が3桁以下になると書式が崩れ、そのまま解釈に失敗します。

`formatTime()` 相当の処理で**年を4桁ゼロ埋めする**よう修正して解決しました。

実データに西暦1000年以前の日付が入っていたのは、
多くの場合はデータ側の異常値（初期値やデフォルト値の混入）でしたが、
**取り込み基盤側がそれで落ちてよい理由にはならない**ので、基盤側で吸収する判断をしています。

## まとめ

5件のうち、**実際の不具合は4件、仕様どおりだったものが1件**でした。

振り返ってみると、共通しているのは次の2点です。

- **境界値（カーディナリティ1、西暦1000年以前）で落ちる**
  正常系のデータでは踏まないので、本番で初めて表面化します
- **JDBC ドライバごとの方言差**（Oracle の日付リテラル）
  共通コードで書かれている箇所ほど、特定の DB でだけ落ちます

いずれもドキュメントを読んでいても分からず、
**ソースを読んで初めて理由が分かる**類のものでした。
OSS をデータ基盤の中核に据える場合、
「ドキュメントに書いていないことが起きたときに、ソースまで降りていけるか」が
そのまま運用の安定度に効いてくる、というのが当時の実感です。
